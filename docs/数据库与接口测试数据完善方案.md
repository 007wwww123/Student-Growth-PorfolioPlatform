# 数据库与接口测试数据完善方案

审查基线为 main 的 e285027。下文的“已有”以仓库中的 MySQL DDL 为准，实际部署库的版本、行数与执行计划需现场核验。功能分支中的表和接口不计入此基线。

## 一、现有八张表

| 表 | 粒度与关键关系 | 优先核验或完善项 |
| --- | --- | --- |
| sys_user | 一个登录账号；学生账号关联 stu_student，username 唯一 | 核对学生账号、学生 ID 与角色的一致性。temp_grant 仅表达有无授权，不能说明授权对象和期限。开发账号脚本重跑会重置口令，须与结构升级分开。 |
| stu_student | 一个 SIS 学生；学号唯一，class_code 关联班级 | 为同步提供可追溯来源；核查学号和班级孤儿引用。身份证目前在主数据和档案字段值中均可能有明文，设计加密迁移时须同时覆盖两处、待确认值和同步读取路径。 |
| org_class | 一个班级；班级编码唯一，现任辅导员决定审核范围 | 延续现任辅导员口径。若需要还原历史学年的归属，再引入带生效区间的班级成员或任职记录。 |
| arc_profile | 一个学生 × 学年 × 板块；三列联合唯一，已有状态、次数、时间、完成度与版本号 | 校验合法状态、完成度区间与撤回次数。对真实待办查询执行 EXPLAIN ANALYZE 后再决定是否增加学年、状态、提交时间和 ID 的组合索引。 |
| arc_field_def | 一个全局唯一字段编码；含来源、角色、校验器、选项、排序和敏感级别 | 当前种子仅覆盖 BASIC 的 16 项。其他五板块逐项补配置，核对每项校验器已注册、枚举值可用、角色可写、SIS 来源列存在，再开放接口。 |
| arc_profile_item | 一个档案实例 × 字段；已有正式值、待确认值及确认人、时间 | 检查孤儿项、跨板块字段、错误 JSON 与正式值/待确认值混用。增加一致性约束前先清理旧行；确认、驳回和并发覆盖都应有回归。 |
| arc_change_log | 一次内容或状态变更 | 保留业务变更职责；按实例与时间复原退回、撤回、重提。在同时间戳下用 ID 稳定排序。受保护字段的旧值和新值必须脱敏。 |
| sys_audit_log | 一次敏感能力调用，可关联操作者、目标及 trace_id | 以查看明文、确认、审核等场景核对操作人与追踪号；审计明细不得复制明文证件或联系方式。 |

审核任务已经通过查询档案实例得到，不宜复制一张待办表。手机号待确认已有 pending_* 字段，两类日志也已分工。优先修复查询中的一个具体边界：当前审核列表的班级过滤从同学年的 BASIC 实例开始；当学生已有主数据、仅有其他板块实例时，列表仍可能漏项。测试应建立这种实例，并让列表和详情权限都按“主数据优先、存量字段回退”判断。

依据：[核心五表](../backend/src/main/resources/db/sql/01_create_core_tables.sql)、[操作审计](../backend/src/main/resources/db/sql/04_create_audit_log.sql)、[学生主数据](../backend/src/main/resources/db/sql/06_create_student_table.sql)、[账号](../backend/src/main/resources/db/sql/08_create_user_table.sql)、[待办查询](../backend/src/main/resources/mapper/review/ReviewTaskMapper.xml)。

## 二、建议新增的表及启用条件

以下为候选设计。按具体业务操作决定建表，暂不调整线上结构。

| 优先级与条件 | 建议表 | 最小设计与验收条件 |
| --- | --- | --- |
| P1，开放照片或其他附件上传前 | arc_attachment | id、所属学生、用途、对象存储键、文件类型、字节数、上传人、状态、创建时间。对象键唯一，按学生与状态索引；绑定前校验所有者、用途及可用性。FILE 数组内的每个 ID 都应能授权解析。 |
| P1，开放导师填写前 | org_mentor_student；arc_mentor_note | 前表记录导师账号、学生、学年、有效期，防止跨学生读写。后表记录所属档案、导师、谈话日期、主题、内容及反馈时间；一条谈话一行，按档案和日期索引。先确定一学年是否多次谈话、一次反馈针对哪一条；仅有单份字段表单时可继续使用字段值表。同步补导师身份与授权入口。 |
| P1，开放多条证书或学术活动录入前 | arc_certificate、arc_event | 各行关联学业板块实例；分别记录证书名称、颁发单位、日期，或活动名称、日期、参与身份。附件关联上述附件元数据。先确认重复判定规则，避免只按名称设唯一键误删同名获奖或活动。 |
| P1，临时管理员授权需要到期或限定范围时 | sys_data_grant | 记录被授权人、授权范围、只读动作、生效与到期时间、签发人、撤销记录。有效范围需在请求时验证，测试授权过期、撤销及跨范围访问。旧 temp_grant 无法推导历史范围，迁移需重新核定。 |
| P2，要求能复现某次归档或导出时 | arc_archive、arc_archive_section | 归档头记录学生、学年、批次、操作者与时间；明细每批每板块唯一，保存档案 ID、批准版本及不可变快照或可取回的快照引用。六个批准版本一次提交；后续更正保留历史批次。若仅需状态锁定，可先沿用 arc_profile.status。 |

## 三、让 OpenAPI 示例可以直接联调

以 [07 学生种子](../backend/src/main/resources/db/sql/07_insert_student_seed.sql)、[09 账号种子](../backend/src/main/resources/db/sql/09_insert_user_seed.sql) 和 [03 字段定义](../backend/src/main/resources/db/sql/03_insert_basic_field_defs.sql) 为基础，统一 [接口契约](../openapi.yaml)、前端 mock 与测试。固定业务身份及状态前置条件；数据库生成的 ID、令牌、traceId、时间戳通过响应捕获或按格式断言。

| 场景 | 测试数据与操作 | 接口与数据库应共同证明的结果 |
| --- | --- | --- |
| 登录与身份 | 1001 使用种子登录名 2024010101；对照无效口令、停用账户、过期令牌、注销后重用 | login/me 返回 1001 对应身份；错误分支按契约区分。过期、停用另设夹具；注销用健康 Redis 验证，独立记录 Redis 不可用时的既有行为。 |
| 基本信息首次查询 | 1001、RJ2401、2025-2026-1；由 SIS 同步姓名、学号、性别、班级 | 成功详情和 UserVO 统一使用种子身份。目前示例中的“林清和／2023010101”与种子不符。区分首次查询和已部分填写；完成度按启用必填字段计算，不固定抄写示例百分比。 |
| 学生保存与字段确认 | 正例只发可编辑字段；单独发送 classId 作为只读反例。设置手机号旧值 A，学生申请 B，辅导员分别确认或驳回 | classId 来源为 SIS，不能出现在学生成功保存样例。待确认时正式值仍为 A，确认后为 B，驳回后仍为 A；在正式响应和审计中分别检查脱敏。两条分支各用独立草稿。 |
| 附件与敏感字段 | 照片先创建归属 1001 的附件，再用返回 ID 替换示例 10231；同时准备不存在、其他学生所属附件。查看明文用专用虚构证件值 | 附件能力未实现前将照片标为未来样例。明文只在获准的 reveal 调用中返回，普通详情保持脱敏，审计可按 traceId 定位。 |
| 审核范围与分页 | cou9001 管 RJ2401、RJ2402；cou9002 管 DZ2401。用 1001 与 1004 在同一学年提交，另建 1001 的第二学年；分别使用 admin 和 admin0 | 本班待办可见，跨班记录不入列表，直接访问也受权限约束；跨学年不串档。多条相同提交时间仍稳定分页。总数依据夹具计算，避免硬编码文档的 12 条。 |
| 状态及日志 | 从独立草稿分别执行提交→撤回→重提→再次撤回，以及提交→退回→修改→重提→通过；另建短退回理由和陈旧版本场景 | 验证状态、次数、版本和双日志；二次撤回、短理由按约定错误码返回。陈旧版本通过两个并发事务构造，不给契约臆加请求头。失败操作不能留下部分状态变更。 |
| 学业等其余五板块与整体归档 | 为每板块设计一份合法草稿及一份字段校验反例；六板块使用同一学生和学年。归档分别准备五项通过、全部通过、另学年的通过记录 | 当前五板块服务中的占位操作按现状记录 501；实现完成后切换为真实成功用例。整体完成须按同学生同学年计算。归档接口、权限与快照方案确认后再发布可执行示例。 |

### 三份数据需要一起修改的位置

- [OpenAPI](../openapi.yaml) 的登录请求示例、BASIC 详情、UserVO、ReviewTaskVO 均应引用同一学生身份。操作示例和 BasicSectionSaveDTO 自带的示例都包含 classId，应同时从成功请求中移出，另加学校维护字段被拒的示例。
- [前端 mock](../frontend/src/mocks/data.ts) 已使用种子学生姓名、学号，但性别使用中文标签，部分证件测试值也与 SIS 种子不同。字段值与展示标签应分开：例如性别存 M/F/U，家庭经济状况存 NORMAL，页面再按 options_json 映射为中文。避免复制真实个人资料到测试夹具。
- 学业保存样例的 goalShort 低于 [学业 DTO](../backend/src/main/java/com/college/growth/academic/dto/AcademicSectionSaveDTO.java) 要求的 20 字。改用达标的正例，并保留 19 字和 20 字两条边界用例。
- 审核示例的 profileId 应取建档后的实际 ID。完成度、待确认值、待办数量需根据前置操作推导；掩码字段和 pendingValue 按角色分别生成示例。若同一局部请求可匹配多个保存 DTO，检查当前 oneOf 的唯一匹配性，以各板块真实请求做契约验证。

## 四、实施顺序与交付检查

1. 用空测试库依序跑 01–09，核对八表、三班、四名学生、八账号、16 项 BASIC 定义；只记录计数与脱敏信息。独立安排旧库升级演练，检查孤儿引用、重复键和非法历史值。
2. 分开维护结构升级、业务基础配置、开发身份种子和测试场景构造。开发口令与测试状态仅进入专用测试库；禁止把 09 当成生产升级脚本重跑。
3. 在契约中按操作与角色命名成功、拒绝和冲突样例。每个样例注明前置种子、登录角色、学年、预期 HTTP/业务码及表断言。手机号审批、审核和日志由真实接口生成；仅对无法通过公开流程建立的前置状态使用专用测试夹具。
4. CI 在一次性 MySQL、Redis 上逐场景执行，校验响应 schema、业务预期和相关表。重跑时重建专用夹具，确保顺序无关。新增表随使用它的读写接口、权限测试及 OpenAPI 示例同批交付。

## 五、基础业务可行性复核与扩展边界

**结论：现有八表可承载基本信息板块从登录到审核的流程。六板块整体归档仍有实现缺口。** 最小交付可以保留现有表结构，先统一待确认值语义并校验主数据，再逐板块扩展。

| 基础动作 | 所需数据或约束 | 验收判据 |
| --- | --- | --- |
| 登录并定位本人档案 | 有效学生账号绑定在读学生；学生班级存在且班级关联正确的辅导员 | 同一学生不同学年各自建档；本班辅导员可审，跨班拒绝。 |
| 填完基本信息 | 16 个配置字段中，8 个标为必填。姓名、学号、性别、民族、身份证和班级由 SIS 提供；专业由班级推导；紧急联系电话由学生填报 | 校验从真实学生种子首次建档到提交的全过程。学校维护字段缺失时应指向主数据补录；不要求学生手工写入只读列。 |
| 首填及修改待确认字段 | 首填、已有正式值后修改、申请清空是三种不同情形。当前首填写正式列并标 PENDING，确认服务却从 pending 列读取；首填没有候选值时确认会把空值传给正式值写入逻辑，驳回则会保留未经确认的首填值 | 推荐所有待审输入写候选区；用状态区分“无申请”和“申请清空”。无旧值时确认得到新值，驳回仍为空；已有 A 时申请 B，确认得 B、驳回保留 A。明确尚未确认的必填值能否通过板块审核，分别断言详情、完成度、审核结果与日志一致。已有 PENDING 且候选为空的行不能一律回填，须先分辨首填和清空请求。 |
| 审核及追溯 | 实例状态、版本、提交/撤回次数与双日志共同承载 | 并发审核只成功一次；同学生同板块跨学年的日志按 profile_id 区分；删除或停用配置后仍能解释旧档案。 |

实现依据：[基本信息保存与提交](../backend/src/main/java/com/college/growth/basic/service/impl/BasicSectionServiceImpl.java)、[字段编解码](../backend/src/main/java/com/college/growth/common/profile/FieldValueCodec.java)、[确认与驳回](../backend/src/main/java/com/college/growth/common/profile/service/impl/PendingFieldServiceImpl.java)。

**后续扩展触发条件。** 普通单值、多选字段优先增配 arc_field_def，保持字段编码稳定；改类型或改含义时新增编码并迁移旧值。出现“一份档案多条记录且每条有自己的日期、作者或附件”时，加关联 profile_id 的明细表。需要按历史口径重现归档时，再加入不可变快照和字段定义版本。列表性能优化以真实数据量和执行计划为依据。结构升级采用新增脚本，先扩展、回填、核对，再收紧约束；测试账号和样例数据独立装载。

## 六、基础业务实施结果（2026-11-27）

基本信息首填和后续修改都先存候选区。显式清空使用 pending_json 中的 JSON null 表示；若历史 PENDING 行的两列候选值均为 SQL NULL，确认或驳回会提示重新填报，避免将未识别的历史值自动清除。提交允许使用候选值，通过审核前须处理启用字段的全部待确认申请，且非推导必填字段须有正式值。审核列表使用学生主数据判班，缺失时回退同学年的历史基本信息。

本轮从空 MySQL 库执行 01–09，基础一致性核对六项异常数均为零。后端 83 项测试通过（包括真实 MySQL 的审核范围回归），前端 35 项 mock 断言及生产构建通过。使用打包后端、临时 MySQL 和 Redis 的 HTTP 验收跑通首填、驳回、确认、清空、跨班拒绝、退回重提、审核通过与注销。

此次交付范围为基本信息基础流程。其他五板块的业务实现及附件、导师关系、不可变归档快照仍按第二节的启用条件推进；保留现有八表结构。
